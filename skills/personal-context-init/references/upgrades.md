# 规范升级

清单 schema_version 与 policy_version 分开：前者是管理文件格式，后者是规则发布版本。未知 schema_version 必须阻塞，不能把它当作初次初始化。

升级基线由清单保存的原始模板正文及 SHA-256 提供，不保存个人文件快照。模板目录按版本保留且发布后不修改。脚本验证模板哈希，但哈希不是数字签名；模板来源可信度仍需人工确认。清单丢失或校验失败时，不做猜测式升级。

## 三方比较

按文件管理块比较旧模板 B、当前内容 C、新模板 N：

- C = B：应用 N。
- N = B：保留 C（用户定制）。
- C = N：无需改写。
- 其余：保守地将整个文件列为冲突，不尝试语义自动合并。

用户块外内容原样保留；README 的用户主题清单也放在管理块外。新的时间戳只写入实际变更的管理 Markdown。相同版本却不同模板内容视为发布错误；禁止静默覆盖不可变版本。

冲突稿由助手准备、用户审阅后，通过 `--resolutions` 传入完整文件。接受上游规则、保留用户规则或融合二者都可以，最终文件必须符合结构要求。用户保留的差异由清单中的 customization 摘要标记，不存其内容。基线更新到新版，因此以后不会反复将同一差异当作刚出现的上游变化。

## 版本范围

当前脚本只自动处理同一主版本内的文档规范升级，拒绝降级。跨主版本或数据结构变化先单独设计迁移，不能只改版本号。任何个人数据迁移都不属于普通模板升级。

先验证计划中的所有文件，再检查计划所依据的文件哈希，防止覆盖后续编辑。执行前再次检查；最后验证通过才写清单版本。普通异常尝试回滚本次写入，不清除其他文件、不使用 git reset。多文件写入不能保证断电原子性；异常中断后先检查和恢复，不继续盲目升级。

未变更的重复运行保持清单时间不变。没有实际变更时不产生提交、备份或日志文件。
